# The Paper Qualifying Exam Is Its Own Domain, Captured Externally

Qualifications is decided by a **Paper Exam**: a 100-question bubble sheet (A–D or A–E), ~491 papers a stage, sat at Zone centres and captured with an external phone-camera grader (ZipGrade today). It is modelled with its own tables rather than as a delivery mode of `assessments`, because a paper result must be recordable for a Rep with no auth user, one exam may be printed in up to four Key versions, every item carries its own Subject tag, and a bubble sheet needs a staging-and-review step that a self-identifying online attempt does not. **Capture is external; grading is always ours** — the tool has no API, so the contract is a roster CSV out and a full per-question export in, re-graded server-side against our own key, with the tool's own totals and key read only to cross-check. Results publish into `student_stage_results.score`/`score_max`/`breakdown`, and Candidate numbers into `students.exam_id`.

## Considered options

- **Dedicated `paper_exams` tables, results published into the existing stage results (chosen).** Every column is non-null for a reason; a Rep with no `auth_user_id` can hold a result; per-item Subject tags and four Key versions need no contortion; the Student and Coordinator surfaces inherit `student_stage_results`' existing RLS, so publishing adds no new access rule. The answer key lives in an admin-only table with no student-readable policy to get wrong, and `get_paper_result` emits `is_correct` always but `correct` only once the exam's review is released — the same discipline as ADR-0002, re-established rather than inherited. Costs a second per-result detail page.
- **A `delivery='paper'` variant of `assessments` + `assessment_attempts`.** Would inherit `/portal/results/[id]`, `get_attempt_review`, the Coordinator results view and admin analytics for free. Rejected: `assessment_attempts.student_user_id → auth.users` excludes the history-only Reps we must record, `assessments.subject` is a single scalar, `question_bank.prompt` is NOT NULL so a 100-item paper needs filler rows per Key version purely to hold a Subject tag, every attempt column (`max_attempts`, `time_limit_minutes`, `violations`, `content_version`) becomes meaningless-but-present, `enforce_aq_mode_match()` and ADR-0002's disjoint-pool guarantee both have to learn a third mode, and 491 rows landing in one afternoon distort `avgScore`, `scoreHistogram`, `modeSplit`, `flagged` and Active Students (ADR-0007).
- **Keep the scores in a spreadsheet and type totals into `registration_stage_results.score`.** What happened before. No Subject breakdown, no re-grade, no audit trail, no Student-visible result, and the per-subject data the programme already collected in 2022 stays un-modelled.

## Notes

- **Candidate numbers are one list per exam.** 001 upward, never reused, so a bubbled number identifies exactly one candidate and a single import may span every centre. `paper_exam_candidates` is the authority (`unique (exam_id, exam_no)`); `students.exam_id` is a mirror, and its existing comment already described exactly this, so pre-2026 zone-scoped values stay put untouched. Allocation is append-only — a re-run after a late school joins continues the list and never renumbers a Rep whose sheet is printed — and refuses past **999** rather than colliding. 3 digits is what the printed sheet holds and what the external tool's pre-filled Answer Sheet Packs require, so no sheet re-issue was needed.
- **The roster carries no record id.** Columns are `First Name, Last Name, Student ID, Class, Custom ID, Principal`; identity is the Candidate number alone. There is deliberately no External ID column, so nothing that identifies a Rep beyond that number reaches a third party's cloud — and the access code (which IS the auth password for code-login Reps) certainly never does. `Class` is the Rep's class (SS1 / SS2). The school rides in `Custom ID` because that is the one free field the capture tool round-trips — the 2025 Zonal Finals export has no School column, but every row carries the school in `CustomID` — and the school is what separates two Reps who share a name at different centres. Principal is last, for the humans distributing and invigilating the sheets; the tool drops it and matching never depends on it. The trade-off is accepted deliberately: with no record id on the sheet, a mis-bubbled digit lands on the wrong Rep and only the name check can catch it, which is what the review page's "matched, but worth a look" list exists for. The `external_id` matching rung is kept for a Phase-2 scanner, which can read a real id straight off the sheet.
- **Nothing is ever dropped.** Every parsed row becomes a `paper_exam_papers` row with a status; commit is refused while any row is unmatched, ambiguous or duplicate, and a discard requires a reason. A second sheet for one student trips a partial unique index and becomes a human decision.
- **The export's column names are undocumented, so the header is sniffed** — aliases for the named columns, and the per-question series found by pattern (a contiguous run from 1) with a data-based tie-break between the response series and the key series. A file we cannot read is refused with every header listed. The resolved mapping is persisted on the import batch. Two things the real 2025 export settled: it interleaves four 100-long series (`Stu1,PriKey1,Points1,Mark1,Stu2,…`), and the two derived ones are excluded **by name** rather than left to the tie-break — `Points` is 0/1 and `Mark` is C/X, both of which parse as plausible letters, so a mis-picked series would be a fileful of silently wrong scores rather than an error.
- **How many bubbles a question has is a property of the exam** (`paper_exams.option_count`, 4 or 5), because both sheets are in use — the 2025 key has an E at item 20 with students shading it and scoring it, and the 2026 sheet is A–D. It matters in both directions, which is why it is recorded rather than assumed: on a five-option paper an E is a real answer, and on a four-option one it is a misread that is read as an unreadable mark and flagged for review instead of scored. The count is saved *with* the key, so the answers are always validated against the number about to be stored; narrowing it while a key still answers with E is refused by the app and by a trigger on each side of the join. The tool's own key column is deliberately read at full range: the clamp models what a sheet can physically carry, and a typed-in key disagreeing with ours is a signal to surface.
- **The key can be read out of the export.** It repeats on every row, so when an exam has no key yet the importer hands the operator those letters to check against the printed key and paste in, instead of sending them off to type 100 answers. Adopting it stays an explicit human act: grading here never means trusting the capture tool's marking.
- **Commit re-grades from the stored responses**, not the staged totals, so a key corrected after staging is picked up; and it sets `outcome` only on insert, so a corrected re-import never silently un-decides a Rep an admin already advanced.
- **A score is a measurement; an outcome is a decision.** The cut writes outcomes only to `student_stage_results` and leaves score/breakdown alone, and "send a school back" now resets a scored row to pending instead of deleting it. Fixed on the way in: three upserts named a conflict target that `20260822090000` had dropped, so per-Rep stage results had been failing with 42P10 and being swallowed; and `markSchoolAndReps` fanned `score: null` to every Rep, which would have erased paper scores on the next school-level save.
- **Ties across the cut are never broken by sort order** — the preview blocks the commit and names the tied schools, so it is settled by widening N or by a Face-off.
- **Phase-2 seam.** Everything tool-specific stops at `readPapers(...) → RawPaper[]`. An in-app scanner produces the same array, flips `paper_exam_imports.source`, and changes nothing downstream.
- **Not modelled:** a Paper Exam does not feed `plan_item_progress` or Active Student, and analytics has no Subject dimension yet.
